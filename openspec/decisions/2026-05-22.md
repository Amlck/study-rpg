## 00:05 — Supabase HEAD 503 sideband — 監測 7 days

Phase 3 R2 cutover (`add-r2-cloud-sync-migration` task 5.6) Chrome MCP smoke 抓到 sideband：6 個 Supabase `HEAD /rest/v1/<table>?select=user_id&user_id=eq.<uuid>&limit=1` 回 **503 Service Unavailable**（player_state / hospital_state / question_bookmarks，一階 + 二階各跑一次共 6 個）。這是 `migrate-from-supabase.ts` 的 row-existence probe（migration banner detection），不是 pullNow 路徑。App 處理 graceful（page render + sync 都正常），但 503 本身需要釐清。

**這不是 Phase 3 regression** — 從 Phase 1 上線就有，只是這次 cutover smoke 才被看到。

**Hypotheses 待驗**（按可能性排）：
1. **Supabase free-tier rate-limit / connection-pool exhausted** — dual-write 流量翻倍 + per-page-load 3 個 HEAD probe，可能撞到 free tier pooler 上限
2. **PostgREST handler 對 HEAD verb 處理有 bug** — 某些 PostgREST 版本對 HEAD + `?select=user_id` 會回 503，改 GET `select=count` 或 `Range: 0-0` 可能就過
3. **Project 進入 idle hibernate** — Supabase free tier 7 天沒寫入會 pause，但 owner 持續 dual-write 應該不會觸發
4. **RLS policy 對 HEAD 的判斷異常** — 罕見，但對 player_state / hospital_state / question_bookmarks 三個都有就不太像個別 RLS bug

**監測動作**（task 5.7 window 2026-05-22 → 2026-05-29）：
- 每次 sign-in 重跑 Chrome MCP smoke 看 503 是否持續
- Supabase dashboard → API Logs 過濾 status=503 看頻率
- 若 503 率 < 5% 且 app 無 user-visible 影響 → log 不動、Phase 4 照走（freezing Supabase rows 後 banner detection 也會自然下線）
- 若 503 率 > 30% 或 user 報 banner 異常 → 切 separate hotfix change 修 detection probe（換成 GET `select=count` + `Prefer: count=exact`）

**Phase 4 readiness 暫定** 2026-05-29 後評估；若 503 sideband 不擋 user flow，flip `VITE_CLOUD_SYNC_BACKEND=r2` 不需修 503 也能進。
